# Доменная модель Order Processing System

## 1. Назначение системы

Order Processing System — система обработки заказов интернет-магазина.

Пользователь может зарегистрироваться, просматривать товары, создавать и оплачивать заказы, а также следить за изменением статуса заказа.

Администратор может создавать товары, изменять их данные и управлять статусами заказов.

При изменении заказа система формирует события. Эти события в дальнейшем будут передаваться через Kafka в notification-service. Notification-service будет имитировать отправку уведомлений и сохранять историю их обработки.

## 2. Основные сущности

Система содержит следующие основные сущности:

- User;
- Product;
- Inventory;
- Order;
- OrderItem;
- Payment;
- OutboxEvent.

## 3. User

User представляет зарегистрированного пользователя системы.

### Поля

- id — уникальный идентификатор пользователя;
- email — адрес электронной почты;
- passwordHash — хэш пароля;
- firstName — имя;
- lastName — фамилия;
- role — роль пользователя;
- createdAt — дата и время создания;
- updatedAt — дата и время последнего изменения.

### Роли

- CUSTOMER — покупатель;
- ADMIN — администратор.

### Бизнес-правила

- email обязателен;
- email должен быть уникальным;
- пароль не хранится в открытом виде;
- новый пользователь по умолчанию получает роль CUSTOMER;
- пользователь не может самостоятельно назначить себе роль ADMIN.

## 4. Product

Product представляет товар, доступный в интернет-магазине.

### Поля

- id — уникальный идентификатор товара;
- sku — уникальный код товара;
- name — название;
- description — описание;
- price — текущая цена;
- active — признак доступности товара;
- createdAt — дата и время создания;
- updatedAt — дата и время последнего изменения.

### Бизнес-правила

- SKU обязателен и должен быть уникальным;
- название обязательно;
- цена должна быть больше нуля;
- денежные значения хранятся с использованием BigDecimal;
- неактивный товар нельзя добавить в новый заказ;
- изменение цены не должно изменять стоимость уже созданных заказов;
- вместо физического удаления товара используется признак active.

## 5. Inventory

Inventory хранит информацию об остатках товара.

### Поля

- id — уникальный идентификатор записи;
- product — товар;
- quantity — физическое количество товара на складе;
- reservedQuantity — количество товара, зарезервированное заказами;
- version — версия записи для optimistic locking;
- updatedAt — дата и время последнего изменения.

### Связи

Один товар имеет одну запись Inventory.

Связь:

Product 1 — 1 Inventory

### Бизнес-правила

- quantity не может быть отрицательным;
- reservedQuantity не может быть отрицательным;
- reservedQuantity не может превышать quantity;
- доступное количество рассчитывается по формуле:

availableQuantity = quantity - reservedQuantity

- при создании заказа необходимое количество товара резервируется;
- при отмене заказа резерв освобождается;
- при отправке заказа физическое количество и зарезервированное количество уменьшаются;
- @Version используется для защиты от одновременного изменения остатка несколькими транзакциями.

## 6. Order

Order представляет заказ пользователя.

### Поля

- id — уникальный идентификатор заказа;
- customer — пользователь, создавший заказ;
- status — текущий статус;
- totalPrice — итоговая стоимость;
- createdAt — дата и время создания;
- updatedAt — дата и время изменения;
- version — версия записи для optimistic locking;
- items — позиции заказа;
- payment — информация об оплате.

### Связи

Один пользователь может иметь много заказов:

User 1 — N Order

Один заказ содержит одну или несколько позиций:

Order 1 — N OrderItem

Один заказ может иметь одну оплату:

Order 1 — 0..1 Payment

### Статусы заказа

- CREATED — заказ создан;
- PAID — заказ оплачен;
- PROCESSING — заказ обрабатывается;
- SHIPPED — заказ отправлен;
- COMPLETED — заказ завершён;
- CANCELLED — заказ отменён.

### Бизнес-правила

- заказ должен содержать хотя бы одну позицию;
- количество каждой позиции должно быть больше нуля;
- заказ создаётся только для существующего пользователя;
- итоговая стоимость рассчитывается сервером;
- клиент не может самостоятельно указать итоговую стоимость;
- при создании заказ получает статус CREATED;
- запрещено напрямую устанавливать произвольный статус;
- изменение статуса должно выполняться через бизнес-методы;
- после создания заказа изменение цены товара не влияет на стоимость заказа.

## 7. Жизненный цикл заказа

Допустимые переходы:

- CREATED → PAID;
- CREATED → CANCELLED;
- PAID → PROCESSING;
- PAID → CANCELLED;
- PROCESSING → SHIPPED;
- PROCESSING → CANCELLED;
- SHIPPED → COMPLETED.

Запрещённые переходы:

- CREATED → SHIPPED;
- CREATED → COMPLETED;
- CANCELLED → любой другой статус;
- COMPLETED → любой другой статус;
- SHIPPED → CANCELLED;
- повторный переход в тот же статус.

### Правила изменения остатков

При создании заказа:

1. Проверяется доступное количество каждого товара.
2. Если товара достаточно, увеличивается reservedQuantity.
3. Если хотя бы одного товара недостаточно, заказ не создаётся.
4. Все ранее выполненные в этой операции изменения откатываются.

При отмене заказа:

1. Проверяется, что заказ разрешено отменить.
2. Зарезервированное количество каждого товара уменьшается.
3. Статус заказа меняется на CANCELLED.
4. Повторная отмена не должна повторно освобождать резерв.

При отправке заказа:

1. Проверяется, что заказ находится в статусе PROCESSING.
2. Из quantity вычитается количество отправленного товара.
3. Из reservedQuantity вычитается количество отправленного товара.
4. Статус заказа меняется на SHIPPED.

## 8. OrderItem

OrderItem представляет одну позицию заказа.

### Поля

- id — уникальный идентификатор позиции;
- order — заказ;
- product — товар;
- productName — название товара на момент создания заказа;
- productSku — SKU товара на момент создания заказа;
- unitPrice — цена одной единицы товара на момент создания заказа;
- quantity — количество;
- lineTotal — общая стоимость позиции.

### Связи

Много позиций могут относиться к одному заказу:

OrderItem N — 1 Order

Много позиций разных заказов могут ссылаться на один товар:

OrderItem N — 1 Product

### Бизнес-правила

- количество должно быть больше нуля;
- цена позиции не может быть отрицательной;
- стоимость позиции рассчитывается по формуле:

lineTotal = unitPrice × quantity

- цена, название и SKU копируются из Product при создании заказа;
- последующее изменение Product не должно изменять старый OrderItem;
- OrderItem не существует отдельно от Order;
- удаление OrderItem не должно удалять Product.

## 9. Payment

Payment представляет условную оплату заказа.

### Поля

- id — уникальный идентификатор оплаты;
- order — оплачиваемый заказ;
- status — статус оплаты;
- amount — сумма оплаты;
- externalPaymentId — внешний идентификатор операции;
- createdAt — дата и время создания;
- paidAt — дата и время успешной оплаты.

### Статусы оплаты

- PENDING — оплата создана;
- SUCCEEDED — оплата успешно завершена;
- FAILED — оплата завершилась ошибкой;
- CANCELLED — оплата отменена.

### Связи

Одна оплата относится к одному заказу:

Payment 1 — 1 Order

### Бизнес-правила

- оплатить можно только заказ со статусом CREATED;
- сумма оплаты должна совпадать с totalPrice заказа;
- сумма оплаты рассчитывается сервером;
- один заказ не должен получить две успешные оплаты;
- после успешной оплаты заказ получает статус PAID;
- отменённый заказ нельзя оплатить;
- завершённую оплату нельзя провести повторно.

## 10. OutboxEvent

OutboxEvent представляет событие, которое должно быть опубликовано в Kafka.

### Поля

- id — идентификатор записи в таблице;
- eventId — уникальный идентификатор события;
- aggregateType — тип бизнес-объекта;
- aggregateId — идентификатор бизнес-объекта;
- eventType — тип события;
- payload — содержимое события в формате JSON;
- status — статус публикации;
- createdAt — дата и время создания;
- publishedAt — дата и время успешной публикации;
- retryCount — количество попыток отправки;
- nextAttemptAt — время следующей попытки;
- version — версия записи для optimistic locking.

### Статусы Outbox-события

- PENDING — ожидает публикации;
- PROCESSING — обрабатывается publisher;
- PUBLISHED — успешно опубликовано;
- FAILED — публикация завершилась ошибкой.

### Типы событий

- ORDER_CREATED;
- ORDER_PAID;
- ORDER_CANCELLED;
- ORDER_STATUS_CHANGED.

### Бизнес-правила

- eventId должен быть уникальным;
- изменение заказа и создание OutboxEvent должны происходить в одной SQL-транзакции;
- бизнес-сервис не должен напрямую отправлять сообщение в Kafka;
- неуспешно опубликованное событие должно быть доступно для повторной попытки;
- успешная публикация переводит событие в статус PUBLISHED;
- повторная доставка события не должна приводить к повторному уведомлению.

## 11. Общая схема связей

User 1 — N Order

Order 1 — N OrderItem

Product 1 — N OrderItem

Product 1 — 1 Inventory

Order 1 — 0..1 Payment

Order 1 — N OutboxEvent

Последняя связь является логической: OutboxEvent хранит aggregateId заказа, но необязательно содержит JPA-связь с Order.

## 12. Транзакционные границы

Создание заказа выполняется в одной транзакции. В эту транзакцию входят:

1. Проверка пользователя.
2. Получение товаров.
3. Проверка доступного количества.
4. Резервирование товаров.
5. Создание заказа.
6. Создание позиций заказа.
7. Расчёт итоговой стоимости.
8. Создание OutboxEvent.

Если какая-либо операция завершилась ошибкой, вся транзакция должна быть отменена.

Оплата заказа выполняется в отдельной транзакции.

Отмена заказа и освобождение резервов выполняются в одной транзакции.

Отправка заказа, списание остатков и создание события выполняются в одной транзакции.
